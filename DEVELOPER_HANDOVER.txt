5. WHAT THE EXISTING APPLICATION DOES
===============================================================================

CRM and contact management:
- Server-rendered browser UI for a local lead/client CRM.
- Contact records include business/contact details, website and social links,
  sector, location/town, source URLs, notes, website status, Google listing
  fields, verification flags, outreach/consent fields, lifecycle, pipeline,
  quote, retainer, hosting, and follow-up date.
- Lead pipeline stages: new, contacted, quoted, accepted, live, lost.
- Lead filters/search, follow-up queue, pipeline counts, recurring-income
  display, and CSV export.
- Profile page with notes, contact channels, source links, verification and
  consent controls, quotation details, hosting/retainer fields, and audit
  history.
- Do-not-contact suppression list uses tenant-scoped hashes for email, phone,
  and Google Place ID matching in the import flow.
- "Not listed" lead finder searches public Facebook/directory pages for leads
  that may not appear in Google Maps; results need human review.

Business website audit:
- Crawls up to 20 accessible same-domain pages in the full audit, subject to
  robots.txt and successful public access.
- Collects page titles, meta descriptions, headings, links, text, social
  profiles, selected business signals, robots.txt/sitemap/llms.txt signals,
  and suspected JavaScript-rendering issues.
- Scorecard categories: website structure, Google Business Profile, linked
  social profiles, content coverage, reputation, and business identity.
- Unverified categories are excluded from the assessed score rather than
  silently counted as zero. Reports expose coverage and confidence limitations.
- Searches for public business/review/competitor candidates; may crawl up to
  three competitor sites with a small page limit.
- Produces ordered recommendations and draft service/location/FAQ content
  briefs. Search demand and rankings are not measured by this analysis.
- Can generate a PDF report using ReportLab and a configurable brand template.

Search and lead research:
- SerpApi-backed Google/Google Maps lookups and ranking checks, with local
  cache/budget controls.
- Live cache-miss lookups reserve a monthly budget slot atomically; cache hits
  use no slot. A reserved slot remains consumed if the lookup fails.
- Town sweeps reserve their per-town and total daily limits before each live
  search; cache hits use no slot, and failed attempts keep their reservation.
- Optional Google Places API lookup when a Places API key is configured.
- DDGS-based free search paths for indicative search and unlisted businesses;
  this route is unofficial and can be rate-limited.
- OpenStreetMap/Overpass can supplement certain town sweeps.
- A town sweep can classify leads by whether search surfaced an apparent
  business-owned website, a social page, a directory page, or no website.
  Search absence is not proof that a business has no website.
- Ranking results are a point-in-time search observation, not guaranteed
  rankings or a universal/personalized position.

Audit queue:
- CRM audits are queued in SQLite and run through a single background worker.
- Audit jobs are tenant-scoped and can be recovered/requeued after startup.
- Audits require a verified contact and a business-owned website.
- Audit status and PDF/audit history appear on the contact profile.

6. TECHNICAL ARCHITECTURE AND FILE MAP
===============================================================================

- crm_web.py
  Local HTTP server and server-rendered CRM UI. Uses Python
  http.server.ThreadingHTTPServer. Default bind is 127.0.0.1; default port is
  8765. It is not a production web framework/API.

- crm.py
  SQLite connection/schema and contact, audit-history, scope, import/list,
  and CSV operations.

- security.py
  Tenant context, AES-GCM text-encryption helpers, suppression HMAC helper,
  and bounded retry helper. The presence of encryption helpers does not prove
  all CRM PII is encrypted in the current write/read paths.

- security_schema.py
  Additive schema migration helpers and tables for tenant IDs, suppression,
  audit/sweep jobs, and API usage. It does not drop existing tables.

- audit_queue.py / sweep_queue.py
  Background audit/sweep queue functionality.

- business_auditor.py
  Main, fuller audit engine and MCP tool server. CRM audit jobs import its
  run_audit(), PDF, and pricing functions. It also exposes audit/sweep
  operations through MCP when run in serve mode.

- town_sweep.py / find_unlisted.py / rank_check.py
  Separate lead discovery, sweep, and search-rank utilities.

- storage.py
  Storage protocol and local filesystem implementation. Local is the only
  implemented backend; non-local backends raise an error.

- scoring.py, researcher.py, web_research.py, auditor.py, server.py
  Earlier or alternate research/audit paths remain in the repository. Do not
  remove or replace them without checking imports and callers. The CRM's
  queued audit path uses business_auditor.py.

- assets/prompts/audit_system.json
  Audit evidence/prompt policy text.

- assets/templates/pdf_brand.json
  PDF brand defaults and logo-path setting.

- tests/test_crm_web_pdf.py
  HTTP-level regression test proving a tenant can download its own PDF but
  receives 404 for another tenant's audit PDF.

The repository does not currently have a tracked README or public frontend
configuration. Use this handover plus source code as orientation, and add
maintainer/deployment documentation after implementation.

8. DATA, PRIVACY, AND SECURITY REQUIREMENTS
===============================================================================

Current persistence:
- SQLite database default: reports/straight_up_digital.sqlite3
- Local generated reports, JSON snapshots, caches, usage files, and PDFs are
  under reports/ (this directory is ignored by Git).
- Audit history stores summary/full audit JSON and report paths.
- MCP job results in reports/jobs are retained for 30 days, capped at 1,000,
  and the oldest results are evicted first. This does not purge CRM audit
  history or generated PDFs.
- LocalStorage is the only active object-storage implementation.
- No production migration or customer-data transfer is included in this work.

Current isolation and limitations:
- The code uses a configured CRM_TENANT_ID and many database operations are
  tenant-filtered. It is a single local deployment context, not a fully
  authenticated multi-customer SaaS service.
- No user login, roles, password/session management, or production
  authentication/authorization layer was confirmed in the CRM.
- The local server binds to loopback and POST handlers reject non-loopback
  requests. Do not remove these protections or expose this server directly to
  the internet.
- The server uses SQLite and local disk; do not assume these provide safe
  multi-instance/serverless persistence.
- Local database, reports, backups, .env, and auditor_config.json are private
  local data/config and are intentionally excluded from Git. Do not copy them
  into a public frontend, build artifact, issue, or handover attachment.
- The real .env was not read for this handover. Never include API keys,
  encryption keys, customer records, reports, or local database contents in
  source control or public build output.
- Fields such as consent, outreach permission, lifecycle, and suppression are
  present. The operator must verify source, lawful basis, consent, retention,
  opt-out and POPIA requirements before using imported contact data.

If migrating database or storage:
1. Agree and document the target schema, tenant mapping, and data fields first.
2. Make a dated, access-controlled backup of the SQLite database and report
   files; verify that the backup can be restored.
3. Run the migration on a copy/staging environment, never first on the only
   production copy.
4. Preserve contact IDs/relationships, tenant IDs, consent/suppression data,
   audit history, PDF paths/content, and timestamps.
5. Compare source/target row counts and representative non-sensitive checks;
   verify tenant access controls and PDF links before switching traffic.
6. Keep the original read-only backup and a documented rollback/switch-back
   plan until the owner accepts the migration.

9. EXTERNAL SERVICES AND ENVIRONMENT CONFIGURATION
===============================================================================

Observed integration paths:
- SerpApi: Google/Maps/search and ranking-related requests. Requires a
  privately configured SERPAPI_API_KEY; usage may incur quota/cost.
- Google Places API: optional lookup; requires GOOGLE_PLACES_API_KEY and the
  relevant API/billing configuration.
- DDGS: free, unofficial search path. Do not promise availability or exact
  results.
- OpenStreetMap Overpass: optional supplementary business search.
- Public business websites: fetched with httpx; crawl limits and robots.txt
  behavior apply.
- ReportLab: PDF reports.
- MCP: business_auditor.py --serve and server.py expose streamable HTTP behind
  an MCP_BEARER_TOKEN check. The token must contain at least 32 characters;
  startup fails if it is missing or too short. Clients must send it in the
  Authorization: Bearer header. The default bind is 127.0.0.1:8000. For remote
  access, use HTTPS through a trusted proxy/tunnel and configure it to preserve
  the authorization header; never expose plain HTTP publicly.

Environment variable names in .env.example include:
- SERPAPI_API_KEY
- CRM_ENCRYPTION_KEY_B64
- CRM_SUPPRESSION_HMAC_KEY
- CRM_TENANT_ID
- AI_DAILY_COST_LIMIT_USD
- CRM_DAILY_AUDIT_LIMIT
- CRM_STORAGE_BACKEND
- CRM_LOCAL_STORAGE_DIR
- CRM_DATABASE_PATH
- CRM_PDF_LOGO_PATH
- MCP_BEARER_TOKEN (required for MCP HTTP; generate a random token locally)
- MCP_HOST / MCP_PORT (MCP defaults to 127.0.0.1:8000)
- CRM_HOST / CRM_PORT (CRM_HOST is in the sample, but crm_web.py currently
  hardcodes 127.0.0.1; CRM_PORT controls the port)
- GOOGLE_PLACES_API_KEY (used by source even though not listed in the sample)
- OVERPASS_API_URL and sweep/search limits

These are variable names only; no secret values belong in this document or
Git. Use deployment secret/environment settings, not frontend variables or
committed config. Review which values the production architecture actually
needs; do not assume every sample variable has an implemented integration.

10. DEPLOYMENT RECOMMENDATION
===============================================================================

Recommended separation:

A. Public marketing site
   - Build as a responsive static/frontend app and deploy to Netlify if that is
     the selected platform.
   - Keep public copy, forms, and assets separate from CRM data and secrets.
   - A public contact form must submit only to a protected endpoint, include
     validation, spam controls, a privacy notice, consent where applicable,
     and a clear confirmation/error state.

B. Private CRM/audit backend
   - Host the Python service on a Python-capable managed host/container, or
     explicitly port its backend functions if an all-Netlify implementation
     is selected.
   - Use a managed database suitable for concurrent production traffic and
     durable object storage for PDFs/reports.
   - Add authentication, user roles, server-enforced tenant ownership,
     CSRF protection, rate limiting, secure sessions, audit logging, backups,
     restore tests, and HTTPS before real customer data is entered.
   - Do not trust a tenant ID supplied by the browser; derive tenant identity
     from the authenticated server-side session.
   - Serve PDFs only after an authorization check for the owning tenant/user.

Netlify-specific caution:
- Netlify frontend hosting does not mean this Python server and local SQLite
  database run unchanged on Netlify.
- Decide whether the Netlify site is only the public frontend or whether the
  backend is being rewritten/ported. Get owner approval for that architecture
  before implementation.
- The repository currently has no netlify.toml or frontend build config.
